# Motion 运动执行框架

一套**声明式路径执行库**：把"双轮差速库"（`F:\stmtest\Lib\motion_ctrl`）与"麦轮库"
（`F:\engineering-training-competition\USER\Hardware\Mecanum.c`）的逻辑互补整合，
用同一套 API 驱动差速 / 履带 / 麦轮三类底盘。最终被 **panzer 履带底盘**使用。

核心理念：路线是一张常量段表（Flash），执行器每个控制周期被 `mf_tick()` 一次——
输入当前位姿，输出车体速度指令。改路线 = 改段表，不碰控制逻辑。

## 架构

```
HAL (电机/编码器/IMU)
  -> 里程计 mf_odom        (位姿 x,y,yaw；两套运动库里程计逻辑的并集)
  -> 段执行器 mf_path      (声明式路径：增量 + 绝对 + 转向)
  -> 逆解 mf_kinematics    (vx,vy,wz -> 各轮线速度 m/s)
  -> 轮速环 mf_pid         (PWM+DIR 模式；驱动器闭环模式跳过)
  -> HAL
```

## 文件

| 文件 | 说明 |
|---|---|
| `mf_config.h` | 编译期宏：底盘类型 / 电机模式 / 航向源，切换底盘只改这里 |
| `mf_types.h` | 位姿、车体指令、声明式段类型（MOVE_DIST/ARC/TURN_TO/TURN_REL/GOTO_XY/GOTO_REL/WAIT/END） |
| `mf_hal.h` | 硬件抽象：motor_cmd / encoder_dist_m / imu_yaw_deg / tick_ms |
| `mf_pid.h/.c` | 位置式 PID（航向环、点到点、轮速环共用） |
| `mf_odom.h/.c` | 里程计（差速/履带/麦轮分支编译，IMU 优先） |
| `mf_kinematics.h/.c` | 逆运动学 |
| `mf_path.h/.c` | 段执行器 |
| `mf_motion.h/.c` | 顶层 API：mf_init / mf_tick / 路径与手动模式 / 单步便捷指令 |
| `mf_hal_panzer.c` | panzer HAL 适配 + 示例路线（模板，含台架核对清单） |

## 底盘切换

```c
/* mf_config.h（或 Keil Define 里定义） */
#define MF_CHASSIS_TYPE   MF_CHASSIS_TRACK    /* 差速: DIFF / 履带: TRACK / 麦轮: MECANUM */
#define MF_MOTOR_MODE     MF_MOTOR_PWM_DIR    /* 框架闭环 PWM / 驱动器闭环速度指令 */
#define MF_YAW_SOURCE     MF_YAW_SRC_IMU      /* IMU / 编码器差分 */
```

轮序约定：`0=左(前左) 1=右(前右) 2=左后 3=右后`。

## 单位约定

距离 m，速度 m/s，角度 deg（多圈连续，逆时针为正），
角速度 deg/s。航向语义与 HWT101 一致。

## 声明式路径示例（履带）

```c
const mf_seg_t route[] =
{
    { .type = MF_SEG_MOVE_DIST, .reset_pid = 1,
      .p.move_dist = { .speed_mps = 2.0f, .dist_m = 6.5f, .heading_deg = 0.0f } },
    { .type = MF_SEG_ARC, .reset_pid = 1,
      .p.arc = { .speed_mps = 1.5f, .radius_m = -0.30f, .d_yaw_deg = -90.0f } },
    { .type = MF_SEG_GOTO_XY, .reset_pid = 1,
      .p.goto_xy = { .x_m = 3.0f, .y_m = -2.0f,
                     .yaw_deg = -90.0f, .v_max_mps = 1.0f, .w_max_dps = 60.0f } },
    { .type = MF_SEG_END }
};

mf_start_path(&mf, route);   /* 10ms 中断里跑 mf_tick() */
if (mf_is_done(&mf)) { ... } /* 段间插入动作（转盘/抓取/等主控） */
```

## ARC 段：为什么航向设定值的来源是关键

弧线段只有**航向**进环（没有横向位置进环），所以"设定值的偏航速率"就等于实际弧半径：

```
实际半径 ≈ 车体真实前进速度 / 设定值偏航速率
```

旧实现取 `yaw_sp = entry.yaw + dist_accum/R`，而 `dist_accum` 累的是**轮上位移均值**
（`mf_motion.c` 里 `(wheel[0].delta + wheel[1].delta)/2`）。履带转弯时履带面比车体多走
（见 `mf_odom.c` 对横向刮擦的说明），这个均值系统性偏大，于是设定值偏航速率偏快、
航向环被迫多转，**实际半径被压成 R/k 且每条弧都往里切**，误差随打滑线性放大。里程计
x/y 走的是打滑已修正的 `ds_for_xy`，但段进度走的是没修正的均值——同一件事两把尺子。

现在（`MF_ARC_XTRACK_EN=1`）：进段时把名义圆弧解算到世界系（圆心 = 进段位姿 + R·左法线，
半径带符号，左/右转一条式子通用），段内设定值取**名义切线航向** = 圆心→车体方位角 +
sgn·90°。它由里程计位置推出，位置积分用的是 `ds_for_xy`，所以设定值的偏航速率天然等于
"真实车体位移/R"。另加一项横向偏差比例（`MF_ARC_XTRACK_K`，dps per m），让"离弧多远"
本身也进环——旧律对与弧等半径的纯横向平移是完全不可见的（误差恒为 0，永不纠正）。
完成判据仍用 IMU 实测航向差，抗打滑且与"转 d_yaw 度"语义严格一致。

量化（`build_verify/mf_path_test/arc_xtrack_sim.py`、`arc_route_sim.py`）：

| 履带打滑 | 旧律每条弧出口横向偏差 | 新律 |
|---|---|---|
| 5%  | −48 mm  | 0~1 mm |
| 15% | −111 mm | 0~1 mm |
| 20% | −136 mm | 0~1 mm |

全链 6 条弧累积：打滑 15% 时终点位置偏差 586 mm → 77 mm。

现场验收看调试口的 `ARC:<段号> EY=<mm> YE=<0.1°>`：`EY` = 出口横向偏差（正=弧外），
`YE` = 出口航向偏差——后者会被紧随的 `MF_KEEP` 直线当基准锁住，所以那条直线会不会
整段走偏就看它。**注意**：`EY` 是机上里程计给出的估计，纯"里程刻度"类误差（比如等效
轨距标定偏差导致的转弯里程刻度）它会跟着一起偏，看不到——那类误差要靠外部基准（场地线/
相机）一次性标定。

## 转段/停车误差：到位容差与进段丢一拍

段完成判据有两条（`mf_config.h`）：直线用 `MF_TOL_ARRIVE_M = 8mm`（`remain <= tol`），
弧线用 `MF_TOL_ARRIVE_DEG = 1°`（IMU 航向差，就是串口 `ARC:` 行的 `YE`）。这两条**只决定
什么时候宣布到点**，不参与轨迹生成。沿路径方向另有两处系统性偏差，量级比容差本身更值得看
（`build_verify/mf_path_test/seg_handoff_sim.py`，直线链 10 段 × 2.112m = 21.1m）：

| 机制 | 机理 | 停稳工况 | 巡航连跑 |
|---|---|---|---|
| 到位容差短装 | 还差 tol 就宣布完成 → 每段少走 tol | −18 mm | 容差被穿越，几乎无感 |
| 进段丢一拍 | 见下 | +27 mm | **+85 mm** |
| 里程刻度 | 轮上里程 ≠ 真值（比例项） | 0.5% → 100 mm 量级 | 同 |

**进段丢一拍**（`mf_path_tick`）：

```c
case MF_SEG_MOVE_DIST: case MF_SEG_ARC:
    if (entered == 0) { p->dist_accum += ds; }   /* 进段那一拍整拍跳过 */
    break;
```

一拍里"谁产生位移"是有归属的：本拍的 `ds` 是**上一拍指令**的结果。进段那一拍因此属于上一段
的尾巴，但上一段已在上一拍结算完、新段又整拍跳过 —— 这一拍位移**两段都不记**。里程表少记
= 车多走，巡航时每转段约丢 9mm（`v·dt`）。

两个反直觉的结论：

1. **收紧容差不会改善**。`8mm→1mm` 在停稳工况让终点误差从 −18mm 恶化到 +48mm；而且 2mm 与
   1mm 结果**完全相同** —— 到点那一拍的位移量子已有约 4mm，容差再小是空的。真正被 8mm 掩盖的
   是**段末减速曲线跟不上**：抛物线 profile 用的加速度与速度斜坡的限幅速率相等（都取
   `acc_mps2`），离散拍下这个跟踪是临界稳定的，再叠加 40ms 轮速环滞后，到点那一刻车速仍有
   ~0.44 m/s（profile 预期 0.19），随后滑停约 40mm。容差 8mm 提前收口恰好抵消了这块滑停，
   把它收小等于把这层抵消撤掉。
2. **"完成判据之后继续累积"必须在真实拓扑上验证**。在 10 段**连续**直线的模型里，连续累计 +
   名义目标逐段累加（残差结转）能把停稳 −18 → +4mm、巡航 +80 → +5mm，看着就是"正解"。但真实
   段表里 MOVE 之间基本都夹着 ARC，而 ARC 段会重新对齐（方向变了，标量残差没有意义）——残差
   几乎没有机会被结转。换到真实路线（`route_fix_sim.py`）实测：只开结转 130.4 → 124.9mm，
   **几乎无效**；与减速裕度同开反而 61.0 → 93.5mm（**更差**）。所以本宏默认 0、不推荐开。

真实路线上的实际收益（`route_fix_sim.py`，参考点 = 段表解析标称终点）：

| 配置 | 位置偏差 mm（无滑） | 位置偏差 mm（打滑15%） | 航向偏差 0.1° |
|---|---|---|---|
| 现状 | 130.4 | 119.4 | 4.6 |
| 仅去掉进段丢一拍 | 126.7 | 189.2 | 6.0 |
| 仅残差结转（`MF_SEG_CARRY_EN=1`） | 124.9 | 187.9 | 5.8 |
| **仅减速裕度 0.6** | **103.9** | 126.8 | **2.7** |
| **去丢拍 + 减速裕度 0.6** | **61.0** | **91.2** | **1.6** |
| 残差结转 + 减速裕度 0.6 | 93.5 | 119.9 | 3.8 |

**唯一机制清楚、单开就稳定收益的是 `MF_STOP_DECEL_SCALE`（推荐 0.6f）**；"进段丢一拍"单独去掉
在两种打滑下符号不一致（无滑略好、15% 明显差），只有配合减速裕度才稳定变好。

量级排序（全链、沿路径方向）：里程刻度（比例项，最大） > 段末减速/滑停 > 到位容差。弧线的横向
误差是另一个轴（见上一节），两者不能互相替代。

## 直线段航向基准：为什么 MF_KEEP 会把误差放大

一段 `MF_KEEP` 直线（段表里所有 MOVE 段都是）的目标航向是**进段那一刻的实测航向**。
这个取法会把上游 ARC / TURN 段残留的航向误差**锁死**，然后沿直线按

    位置偏差 ≈ 航向误差 × 直线长度

放大。真实路线上最长的两段是 5.5m 与 5.34m，逐段诊断（`build_verify/mf_path_test/_dbg_speed.py`）
量到它们分别贡献 **+66.7mm / +56.1mm** —— 这是全链终点偏差里最大的一项，比弧线横向误差
（每条弧 0~2mm）和段间里程记账误差都大一个量级。

`MF_SEG_NOM_HEADING_EN = 1` 改为让 MOVE 段保持**路径标称航向**：起点用实测航向初始化，
之后每过一条 ARC 加它的 `d_yaw_deg`、每过一个 TURN 赋它的目标角（纯几何累积，不依赖 IMU
持续读数）。于是直线段会**主动把上游误差纠回来**，而不再是锁定并放大。

| 全链终点位置偏差（mm，k=1.00 / 1.15） | A 连续跑 | B 每段停(18次) | **C 大段末停(6次)** |
|---|---|---|---|
| 关（原行为） | 188.5 / 172.2 | 190.5 / 130.3 | 159.1 / 160.0 |
| **开** | 15.0 / 30.5 | 64.1 / 51.3 | 62.5 / 76.0 |
| 开 + `MF_STOP_DECEL_SCALE=0.6f` | 10.7 / 22.2 | 7.8 / 5.2 | **4.9 / 18.4** |

终点航向偏差 0.94° → 0.00°。量化脚本 `build_verify/mf_path_test/speed_unify_sim.py`。

> **模式 C 是现在固件的自测工况**（见下节）：停等从「每个运动段后」改成「每张 nav 表末尾」，
> 18 次 → 6 次。它真正的价值不在终点偏差那几个 mm，而在**白走里程**——WAIT 段里只进 pose、
> 不进段进度的位移从 545.6mm 掉到 153.6mm，再叠减速裕度 0.6 掉到 **32.1mm**。

同一批仿真还给出两个**否定**结论，别在这上面花时间：

- **「ARC 与 MOVE 同速」（弧线由 1.5rps 提到 2.0rps）不是好方案**：连续跑 188.5→70.0mm
  看似有效，但**自测模式下反而更差**（190.5→225.8mm）；何况转弯速度 +33% 会让真实履带
  侧滑加剧（仿真里弧线横向误差已经 2.0→3.0mm）。
- **多段前瞻（lookahead）零收益**：把 `seg_next_entry_speed` 从「看一段」扩到「看 2~3 段」，
  结果与现状**逐位相同**。本段表没有「需要提前更远减速」的场景，现在的「只看一段」够用。

前提：标称航向的基准来自**路径起点的实测航向**。若出发点航向本身有系统偏差，车会一路朝
「错了同样多」的方向跑 —— 现场先空跑一圈，逐段核对串口 `ARC:` 行的 `YE` 是否收敛。
置 0 = 回原行为，供 A/B。

## 自测停等粒度：为什么改成「只在大段末停」

test/route 的自测序列 `1→6→2→3→4→8→7→5` 共 20 个运动段。原实现（`Nav_GearTable` 展开时）
在**每个运动段之后**都插一个 `SEG_PAUSE(3s)`，于是全链 20 次停等、21 次起步。

但这与真机比赛剖面不一致：比赛时是**逐条 nav 命令**下发，表内段间连续跑，只在每条 nav
的首末起步/停车。所以逐段停的自测数据**不能外推到比赛**。改成只在每张 nav 表末尾插一次：

```c
/* Selftest/selftest.c: SELFTEST_PAUSE_EACH_SEG */
#define SELFTEST_PAUSE_EACH_SEG  0u   /* 0=只在大段末停(默认)  1=逐段停(旧, A/B 用) */
```

插桩只发生在**段表拷贝路径**上，而 `Nav_GearTable()` 在 `speed_gear==0` 时直接返回 flash
原表（不拷贝）——所以开停等必须把 `SELFTEST_GEAR` 设成非 0，代价是段速被强制覆盖、不再是
比赛剖面。`SELFTEST_PAUSE_MS>0` 而 `SELFTEST_GEAR==0` 会直接 `#error`。

判据是「下一项已经是 `MF_SEG_END`」——表内段间连续跑，空表（2 NAV_TO_BUCKET）首项即 END，
循环当场 break，不会插入。用 `build_verify/mf_path_test/verify_gear_table.py` 逐表核对展开结果：

| 策略 | 运动段 | 停等 | 起步 | 最长展开表 | 白走里程(滑行) |
|---|---|---|---|---|---|
| 逐段停（旧） | 18 | **18** | 19 | 19 项 | 545.6 mm |
| 大段末停（2026-09-21 前的默认） | 18 | **6** | **7** | 11 项 | **153.6 mm** |
| 大段末停 + 减速裕度0.6 | 18 | 6 | 7 | 11 项 | **32.1 mm** |
| 不停等（**现行**，见下节） | 18 | **0** | 7 | 原表长度 | WAIT 内白走消失 |

缓冲 `NAV_GEAR_BUF_LEN`：比赛形态 12（`car_config.h`），自测插停等时切到 24，
对最长表（tbl_bomb 展开 11 项）绰绰有余。

**为什么停等会偷里程**：不是停等本身算错，而是 `mf_path_tick` 只在 MOVE/ARC 段累加
`dist_accum`，WAIT 段 3 秒（300 拍）里车体的任何挪动——减速尾巴、惯性滑行、履带回弹——
全部进了 `pose.x/y`，一分进不了段进度，成为「白走里程」。下一段从 0 重新计，不会扣回去，
所以每段白走一点、线性叠加。起步次数越多，这项越大。

现场用串口 `PD:` 行可直接读出（`SEG` = 本段实际位移，`PAUSE` = 停等期间挪了多少，
`TOT` = 白走里程累计）。

### 现状：大段末停等也已关闭（2026-09-21）

现场实测新固件「终点航向未改善、其它路线反而更差」，先把停等这个变量排掉，于是把
`SELFTEST_PAUSE_MS` 由 `3000u` 置 **`0u`** —— `Selftest_TablePost()` 的插桩分支整体被裁掉
（`#if (SELFTEST_PAUSE_MS > 0u)` 不成立），段表回原版形态，一条 nav 跑完立刻承接下一条，
大段之间不再有 3 s 静止窗口。

- 自测推进不受影响：`Selftest_NextNav()` 靠 `NAV_DONE → Nav_DoRequest` 推进，与 WAIT 段无关。
- 失去 `PD:` 白走里程诊断行（它在 WAIT 段内取样）。但 `SEG:<段> ST=1 X Y YAW` 由
  `Car_SegChange_Log` 每段进段打印，**逐段落点数据仍然完整**。
- 恢复停等只需改回 `3000u`（并同时把 `SELFTEST_GEAR` 设成非 0，见上节）。`Car_Nav_Task` 里
  `mf_is_waiting()` 的堵转豁免是**无条件**的（WAIT 段本来就要求车体静止，不豁免则停等
  与 `NAV_STALL_MS=3000` 同宽时会在每次停等结束时误报 `NAV_FAULT`），不用额外保留。

## 差速前馈补偿：转弯半径旋钮是怎么定出来的

**现象**：ARC 出口横向偏差 EY 恒为正（往外飘），且左右不对称。

**根因**（2026-09-20 实车串口日志，`build_verify/field_log_20260920.txt` + `analyze_field_log.py`）：
履带转弯时**内侧履带刹不住、外侧履带跟不上**，两侧叠加后实际差速只有指令差速的 0.74~0.89：

| 转向 | 跟踪比(实际/指令) | ARC 出口 EY | ARC 出口 YE | 内侧轮超调 |
|---|---|---|---|---|
| 左转 | 0.889 | 110~114 mm | ~0 deg | +30~+64 |
| 右转 | 0.742 | 150~159 mm | ~−4.1 deg | +30~+83 |

右转明显更差（右侧履带做内侧时超调是左侧的 2 倍多），属**硬件/机械不对称**
（张紧、轮径、电机或制动能力），不是控制增益问题 —— 轮速环已是闭环
（`wheel_kp=0.6` / `wheel_ki=7.0`），稳态误差仍有 21%，说明到了物理极限。

**补偿**：按转向方向放大差速指令。系数有两个口径，取 EY 反推的保守值
（WHEEL 是瞬时快照且在瞬态，EY 是整弧积分结果更可信；过补偿会反向，宁可保守）：

- WHEEL 瞬时：左 1/0.889=1.125，右 1/0.742=1.348
- EY 反推：左 (0.9425+0.112)/0.9425=1.119，右 (0.9425+0.155)/0.9425=1.164

即现值 `MF_DIFF_BOOST_POS=1.12` / `NEG=1.16`。**副作用**：TURN 原地转同比例加快
（IMU 闭环判完成，只影响转速不影响终角）；嫌猛可单独给 TURN 段限速。

⚠️ **EY 是 pose 口径的读数**（`EY = rho − arc_r_abs`，rho 来自 `ds_for_xy = ds_enc×ratio`），
含比例误差，只能用来定"补多补少的方向"，**不能拿它判绝对半径** —— 判绝对半径要用
`build_verify/arc_radius_probe.py`（口径无关）或卷尺量 90° 弧的弦长（R = c/1.414）。

## 返程与终点航向：-180° 从哪来、trim 怎么用

**-180° 是几何真值**：扫码后的 `GYRO_ZERO` 把当时车头朝向定义为 0°，出发首段沿该方向前进，
于是 -180° = 与出发首段严格反向，IMU 直接可读，不是拍脑袋的常数。

**为什么必须写死绝对角**：原全表都用 `MF_KEEP` 继承推算值 `nom_yaw`，于是终点停在什么角度、
停在车道线的哪一侧，都取决于推算链攒下多少残差。想要确定的终点航向，就得给最后的段注入
绝对真值，而不是指望前面调准。

**`NAV_RETURN_LEG_YAW_DEG` 一次管两件事且必须同值**：
① `tbl_return` 长直线的行进目标（决定终点位置偏哪侧）；② 表尾 `TURN_TO` 的停车姿态
（决定终点 POSE 的 YAW 读数）。给两个不同的值，车会先斜着走到点位、到位后再原地掰正。

**`NAV_RETURN_TRIM_DEG`（现场标定项，默认 0）**：写回标称 -180 后若车实物仍系统性偏一侧，
说明 IMU 读数与真实车体朝向之间还有刻度/零点误差 —— 这类误差闭环看不见（它只保证"读数=目标"），
EY 行和 POSE 行也看不出来。**不要去加 PID 增益**，按实测横向偏差换算成角度填一次即可：

```
trim(度) = ΔY / 93.2
ΔY   = (终点 POSE 的 Y) − (标称终点的 Y)     ← 两个都是机上 odom 值，直接相减
93.2 = 5341mm × π/180                       ← 这条腿上 1° 航向偏差对应的横向位移
```

推导：沿航向 ψ=−180°+ε 走 L，Y 向位移 ≈ −93.2·ε；要把 ΔY 抹平需 −93.2·trim = −ΔY，
故 trim = +ΔY/93.2。推导只用 odom 坐标，与实车"左右"叫法无关 —— 填符号时用两个 Y 读数相减，
别用肉眼判断。

**同向 or 镜像（会改 trim 符号）**：两条实物观察看起来矛盾，判据并列：
(a) 出发后第一个 90° 拐弯、站在出发点看是**向左**，而 `tbl_bomb` 首拐是 `ARC(+TURN_RADIUS_M)`
（odom 里 yaw 0→+90 = 逆时针 = 左转）⇒ **同向、无镜像**。这条最可靠：干净的二元判断，
且与"整批段表能在实场跑通、任务点对得上"一致（真镜像则整条路线会跑到镜像位置）。
(b) 终点偏出的一侧被描述为"车的右手边"，按字面会推出镜像 —— 但"左右"极易被观察站位搞反：
站在起点沿出发方向看、或站在终点**迎车**看，观察者的右手边都恰好是 −Y 侧，两种站位下
(a)(b) 同时成立，不必引入镜像。

**30 秒定案（不依赖任何左右叫法）**：车静止上电读 POSE 的 YAW → 用手把整车从正上方看
**逆时针**转约 90°（车头从 12 点转到 9 点）→ 再读 YAW：≈+90 同向，≈−90 镜像。
稳妥流程：先按 ΔY/93.2 填，看**实物**残余偏差 —— 变小则对，变大就翻符号重跑一次（一次即定）。

**±180° 卷绕陷阱**：trim 为负时目标越过 −180（如 −182.6），控制完全正常
（所有航向误差都过 `mf_wrap_deg`），但 POSE 会显示 **+1774** 而不是 −1826 —— 同一物理方向。
验收看实物（角尺/场地线），别因为显示 +179x 就以为车错了方向。

## track_width_m 的四处作用链与禁忌

**它不是"里程标定旋钮"，而是整条转向链的全局增益**，改它等于同时改 4 个增益：

| # | 位置 | 表达式 | 后果 |
|---|---|---|---|
| 1 | `mf_kinematics.c:25-26` | `wheel_out = vx ± wz·W·0.5·boost` | 转向差速 ∝ W |
| 2 | `mf_odom.c:40` | `dtheta_enc = (dR−dL)/W` | ratio 的分母 |
| 3 | `mf_odom.c:69,73` | `ratio = dyaw/dtheta_enc`；`ds_for_xy = ds_enc·ratio` | 弧上 pose 位移 ∝ W |
| 4 | `mf_path.c:272,289` | `EY = rho − arc_r_abs`；`wz += 250·EY` | pose 尺度变 ⇒ EY 尺度变 ⇒ 横向增益变 |

`ratio_raw = W /(k · W_eff)`，硬钳 [0.5, 2.0]（`mf_odom.c:71-72`）。取 k=3.41、W_eff=0.18：

| W | ratio_raw | 实际 ratio | 弧上 `ds_for_xy` | 转向差速 |
|---|---|---|---|---|
| 0.18 | 0.293 | 0.5（钳住） | 0.5·ds_enc | 0.72× |
| 0.25 | 0.407 | 0.5（钳住） | 0.5·ds_enc | 1.00× |
| 0.614 | 1.000 | 1.0（解钳） | 1.0·ds_enc | 2.46× |

⇒ W ≤ 0.307 时里程计完全等价（都顶在钳位下限），所以 0.18 与 0.25 的里程/EY/落点**逐位相同**，
唯一差别是转向差速 ×0.72（半径 ×1.39，从"切内"变"甩外"）——
**0.18 不是"更对"，它只是把车转不动了**。

**0.614 实车事故（2026-09-21，已回退 0.25f）**：ratio 从 0.5 一次性跳到 1.0
① 弧上 pose 位移翻倍 ② EY 翻倍 ⇒ `250·EY` 顶满 `max_wz_dps=150` ⇒ 持续来回打舵 = **蛇行**
③ 逆解差速 ×2.46 ④ `dtheta_enc` 分母小 2.46 倍 ⇒ ratio 噪声 ×2.46。
症状指纹：直线段走 `mf_odom.c:63` 的分支（`|dyaw|<0.05°` ⇒ `ds_for_xy = ds_enc`）与 W 无关
⇒ 表现为 **"只有转弯的路程不对"** ✅ 与实测一致。

**禁忌**：
1. **禁止拿 `track_width_m` 调转弯半径** —— 半径旋钮是 `MF_DIFF_BOOST_POS/NEG`
   （boost 只乘在 `mf_kinematics.c:22` 的命令侧，完全不进里程计）。
2. **改 W 前必须先台架定 k**：下发 `MF_M_DIST(43)`（= 2.867 轮转 = 1.351 框架米）量实物位移：
   ≈1.35m ⇒ k≈1，W 该填 0.18；≈0.40m ⇒ k≈3.41，才轮到 0.61。**k 未定就填任何 W 都是猜。**
3. 治本 = 拆常量：W 只作逆解力臂；odom 改 `ds_for_xy = ds_enc/k` 并删掉 `ratio` 段
   （航向已 100% 来自 IMU，`ratio` 这个"用 IMU/编码器航向差估滑移"的量在 k 未知时没有信息量）。

## 别踩的坑（代码注释精简后，这些约束集中放在这里）

| 坑 | 后果 |
|---|---|
| 自测上电起跑**必须**投递到命令信箱，不能直接调 `Nav_DoRequest()` | 会在 `mf_init()` 之前把段表挂到未初始化的 mf 上，随后被 `mf_path_init()` 连同 state 抹掉 ⇒ 车一动不动，3s 后堵转看门狗报 `NAV_FAULT` |
| ARC 横向项**必须**乘 `arc_sgn`（左 +1 / 右 −1） | `e_y` 恒正=弧外、不分左右；漏乘会把右转弧推向弧外（实测右转 EY +103 vs 左转 +77）。仿真 `arc_xtrack_sim.py` 只有左转用例，这个符号错在仿真里不会暴露 |
| `track_width_m` 不是里程标定旋钮，别拿它调半径（见上一节） | 实测 0.25→0.614 ⇒ 弧上 pose 位移翻倍 ⇒ `250*EY` 顶满 150dps ⇒ **持续蛇行**，且弧上里程翻倍 |
| 停等改回非 0 时必须保留 `Car_Nav_Task` 里 `mf_is_waiting()` 的堵转豁免 | WAIT 段内车体静止会撞 `NAV_STALL_MS`(3000) ⇒ 每次停等结束时报 `NAV_FAULT` 中途停车 |
| 转台应答判据只认"回显功能码 0xFD + 帧尾 0x6B" | 旧判据 `Rxbuffer6[0]==0x11` 是错的 —— 应答是 `[addr][0xFD][状态][0x6B]`，首字节是地址 ⇒ OK 恒 0，明明链路通却显示"驱动器没应答" |
| `TURNTABLE_BOOT_DEG` 别改成 90（即使收车后转台停在回正位） | 码 3 是 57°，会出现"目标 < 零点"的负脉冲，绝对模式表达不了；那种情况必须改用相对模式 |
| 返程腿 `SEG_MOVE_HD` 的绝对角与表尾 `TURN_TO` **必须同值** | 不同值 = 车先斜着走到点位、到位后再原地掰正（多一次行为，横向不再对称） |
| `MF_STOP_DECEL_SCALE=0.6` 必须配 `MF_SEG_NOM_HEADING_EN=1` | 单独开反而更差（159→170mm）：它治"段末速度收不住"，而段末高速留下的航向漂移要靠标称航向才不被后续长直线锁死 |
| ARC 完成判据只看 IMU 转角（`remain_yaw ≤ 1.0°`） | 半径误差**不会**变成航向误差，只会变成位置误差 ⇒ 现场看不到任何告警，表现为"贴内道/出线"；每条弧还允许欠 1.0° 就判完成（弧长 16.4mm） |
| 转台上电零点对齐必须在 TIM5 启动之前、驱动器自检完成之后（约 1s） | 顺序错了零点不恒等，第一条命令可能转好几圈 |
